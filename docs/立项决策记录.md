## 1. 结论摘要（TL;DR）

**值得做，但绝不做「更大更强的电商」——做「更聪明的购物方式」。**

正面与淘宝/京东/拼多多拼 SKU 广度、供应链、流量是必败之战（没有那个资本盘）；智购已经积累的**差异化资产不是品类，而是「AI 全链路原生能力 + 工程化可信度」**。C 组 12 项中，**值得做深的只有 3 项**，其余 9 项应明确放弃或挂起——不做全铺开，把 3 项做出实测数据、做出面试可深聊的系统级闭环，这既是产品差异化的正确姿势，也符合「简历项目做深、不做宽」的纪律。

## 2. 差异化竞争分析（资深 PM 视角）

### 2.1 三个巨头的护城河与盲区

| 平台 | 护城河 | 结构性盲区（智购的机会） |
|---|---|---|
| 淘宝 | 全品类 SKU + 淘宝直播 + 逛逛内容 + 阿里妈妈广告体系 | AI 是「插件」（问问/千牛工具），**不是主链路**；中小商家 AI 经营工具分散、贵 |
| 京东 | 自营供应链 + 物流时效 + 京喜/云言犀客服 | 场景服务浅（衣橱/本地生活/社群无深度）；AI 客服是规则+LLM 拼盘，非购物全链路 Agent |
| 拼多多 | 社交拼团 + 百亿补贴 + 极致低价心智 + 砍一刀裂变 | 「低价优先」压死品质/体验创新；AI 应用集中在比价与补贴，无「帮用户更聪明购物」心智 |

### 2.2 智购的差异化资产盘点（已具备，勿忽视）

1. **AI 全链路 Agent 化（29 工具已就绪）**：对话导购、凑单优化、送礼助手、比价、图片搜款、售后助手、物流管家、使用周期、经营大脑（预测/选品/定价/营销）、供应链预警/补货/异常处理、客服评论管理、拼团 Finder——大厂把 AI 当功能点，智购把 AI 当**交易主链路**。
2. **工程化可信度（简历核心资产）**：容量模型实证（单机可解释容量 + 扩展比 1.53x）、限流熔断降级（BFF 零侵入、7ms 快失败）、SLO 错误预算大盘、金额加密落库、XSS 防护、故障演练闭环、坑记录全量（#1-#63，条条带实测数据）。
3. **交易闭环真实可用**：订单状态机、支付沙箱幂等、outbox 最终一致性、售后全流程、RocketMQ 链路——不是 Demo，是能跑通全链路的系统。
4. **场景垂类雏形**：本地生活（门店）、衣橱家居、内容社区、会员钱包——垂类场景是大平台不愿意做深的地方。

### 2.3 差异化定位一句话

> **「智购 = AI 原生购物操作系统」**：别人是「你来搜、我给你推」，智购是「你的购物助手替你搜、替你比、替你决策、替你经营」。

## 5. 建议立项方案

### 5.1 立项范围（3 个做深点，串行推进）

| 优先级 | 立项 | 模块 | 预估 | 借力 | 验收（带实测数据） |
|---|---|---|---|---|---|
| P0 | **AI 衣橱管家**：拍照识衣（VLM 单品提取）→ 结构化衣橱 → AI 每日穿搭（天气/场合）→ 搭配加购闭环 | closet-service + ai-orchestrator + product | 1-2 周 | wardrobe 工作流 + OpenTryOn 试穿预览 | 20 件衣物识别准确率、穿搭生成可用率、加购转化链路实测 |
| P1 | **数字人主播**：商品自动解说（RAG+LLM）→ TTS → 数字人 → 边看边买 | community-service + ai-orchestrator | 1-2 周 | Streamer-Sales 编排 | 解说生成 P95、无重复话术率、直播加购闭环 |
| P2 | **商品知识图谱 KG×RAG**：商品/属性/意图三元组 → Neo4j → 反常识推荐 + 主动提醒 | ai-orchestrator + marketing + user | 2-3 周 | OpenBG schema + FolkScope | 推荐点击率对照实验（KG 增强 vs 纯向量）、Recall@10 |

### 5.2 明确不做（诚实清单）

- AR/VR 真试穿（许可/硬件门槛）、分期/保险/理财（合规）、个人购物大模型/联邦学习（烧钱无边界）、手势识别（无场景）、快递代收/以旧换新（线下履约依赖）。

### 5.3 立项原则（对齐「简历项目做深」纪律）

1. **借力不造轮子**：算法全用开源（wardrobe/OpenTryOn/Streamer-Sales/OpenBG），工程量在接入编排 + 业务闭环 + 工程化验证。
2. **每条坑记录带实测数据**：识别准确率、生成 P95、转化率对照——面试能深聊。
3. **不做演示片**：每个立项都要真实打通（识衣→穿搭→加购落单；解说→直播→边看边买），禁止「以后再说」。
4. **每块独立提交 + 三件套**：延续既有纪律。

## 8. 用户视角拷问（2026-10-22 追加，推翻 §5 部分立项）

> 用户追问：「这些功能有用吗？好用吗？有没有 alpha moment？」——诚实评估后，§5 的三个立项多数不达标，重新校准。

### 8.1 三标尺评估（有用性 / 好用性 / alpha moment）

| 原立项 | 有用吗 | 好用吗 | Alpha moment | 诚实结论 |
|---|---|---|---|---|
| AI 衣橱管家 | ⭐⭐⭐ 对「衣服多、选择困难」人群真有用；随手穿人群无感 | ⭐⭐ **冷启动痛苦**：拍照录入 20-50 件衣物，多数用户死在第一步；识别误差需人工校对 | ⭐⭐⭐ 潜力（3 件衣→5 套搭配→一键加购），**被冷启动挡住，够不到** | **降级 P2**，且必须先解决「零录入」（从购买记录/浏览历史自动建衣橱，不拍照） |
| 数字人主播 | ⭐ 对用户几乎无感；对商家是降本 | ⭐ AI 念稿主播用户反感——**行业已证伪**（抖音/淘宝大量 AI 直播用户跳过） | ⭐ 用户侧几乎不可能产生 | **放弃单独立项**；解说能力作为商品详情/直播的副产物保留 |
| 商品知识图谱 | 不可直接感知（技术底座） | 取决于封装场景 | 取决于封装：封装成「省钱提醒」才有；封装不好=骚扰推送 | **不作独立立项**，降为「省钱助手」等场景的技术支撑 |

### 8.2 真正的用户侧 alpha moment 候选（冷启动为零 + 已有底座 + 第一屏可感知）

| 候选 | 为什么有 alpha moment | 智购已有底座（不用造） | 优先级 |
|---|---|---|---|
| **AI 省钱助手**（比价+历史价格+降价提醒+最优凑单满减） | 省钱是电商普世痛点；第一屏就懂（「帮你算出了最优凑单，省 35 元」）；每次省钱=一次 wow | compare_prices（比价）、凑单优化器（optimize_cart）、推荐引擎 | **P0 首推** |
| **Agent 定时购 / 对话即购闭环**（「每天早上下单一杯 15 内咖啡」→自动下单） | 懒人刚需；一句话交代→自动执行=明确 alpha moment | 一键代下单（用户确认流）、JWT 下单链路 | **P1** |
| **AI 售后管家（主动解决问题）**（快递异常/商品问题→自动发起售后） | 被动式 AI 主动替用户解决麻烦=强 wow；用户不用发起任何操作 | 售后助手（aftersale 全流程闭环）、物流管家（延误预警） | **P1** |
| AI 衣橱管家（零录入版） | 需先解决零录入，否则够不到 | closet-service（人录+规则） | **P2 降级** |

### 8.3 修正后立项原则（用户视角红线）

1. **冷启动必须为零**：任何要用户先录数据/拍照/配置的功能，先找「从交易数据自动生成」的路径，否则不立项。
2. **第一屏可感知价值**：打开就能看到「帮你省了 X 元 / 帮你解决了 X」的字样，不做埋在三级页面的功能。
3. **错误不骚扰**：主动提醒类默认关闭、可一键暂停；每次主动触达必须带来可量化价值（省钱/省时/省麻烦）。
4. **用户价值 > 商家价值 > 技术叙事**：面试叙事是结果不是立项理由；先问「用户为什么用我，不用淘宝」。

### 8.4 修正后待确认决策点

2. 省钱助手首发范围：比价+凑单建议（快）还是含降价提醒/历史价格（需采集）？

## 1. 目标与验收

**一句话**：让用户打开省钱助手第一眼就看到「本月帮你省了 X 元」，并能一句话关注降价、一键按最优方案结算。

| 验收项 | 标准（带实测数据） |
|---|---|
| 历史价格 | 在售 SKU 每日快照入库；`GET /price/history?skuId=` 返回 7/30 天趋势 + 历史最低价（对比现价算出「比最低贵 ¥X」） |
| 降价提醒 | 用户**主动关注**（targetPrice 可选）→ 每日检测 → 降价命中写站内信（`price_notice`），H5 红点可见；**不骚扰=关注制，默认零推送** |
| 省钱汇总 | `GET /cost-saver/overview`：本月累计节省（券实省+比价最优差+降价已省）+ 进行中降价提醒 + 最优凑单建议；H5 `/cost-saver` 第一屏可感知 |
| AI 对话 | ai-orchestrator 新增 `price_alert` 工具：关注/取消/查降价；system.md 触发词接入 |
| 冒烟闭环 | 造数→采集→关注→模拟降价→提醒生成→overview 汇总 全链路 1 条命令可复验 |

## 3. 数据模型（product-service 分库 zhigou_product）

```sql
-- 历史价格快照（A 块）
CREATE TABLE price_history (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    sku_id      BIGINT NOT NULL,
    price       BIGINT NOT NULL COMMENT '售价(分)',
    snapshot_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    KEY idx_sku_time (sku_id, snapshot_at)
) COMMENT='SKU 历史价格快照';

-- 降价关注（B 块）
CREATE TABLE price_alert (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id      BIGINT NOT NULL,
    sku_id       BIGINT NOT NULL,
    target_price BIGINT NULL COMMENT '期望价(分)，NULL=任意降价都提醒',
    watch_price  BIGINT NOT NULL COMMENT '关注时价格(分)',
    status       VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',  -- ACTIVE/PAUSED/OFF
    created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_sku (user_id, sku_id)
) COMMENT='用户降价关注';

-- 降价站内信（B 块）
CREATE TABLE price_notice (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id    BIGINT NOT NULL,
    sku_id     BIGINT NOT NULL,
    old_price  BIGINT NOT NULL,
    new_price  BIGINT NOT NULL,
    read_flag  TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    KEY idx_user_read (user_id, read_flag, created_at)
) COMMENT='降价提醒站内信';
```

## 4. 接口清单

| 接口 | 方法 | 说明 | 归属 |
|---|---|---|---|
| `/price/history?skuId=&days=` | GET | 趋势（每日价格序列）+ 最低价 + 现价对比 | product A |
| `/price/alert` | POST | 关注（body: skuId, targetPrice?）幂等 upsert | product B |
| `/price/alert/{skuId}` | DELETE | 取消关注 | product B |
| `/price/alert/mine` | GET | 我的关注列表（含当前价/最低价/是否已降） | product B |
| `/price/notice/mine?unreadOnly=` | GET | 降价提醒站内信 | product B |
| `/cost-saver/overview` | GET | 省钱汇总（本月节省 + 提醒 + 凑单） | product C |
| BFF `/cost-saver/*` + `/price/alert/*` | 透传 | X-User-Id 注入 + rawBody（19 位 id 纪律） | BFF C |

**19 位 id 纪律延续**：所有响应 id 字段 @JsonSerialize(ToStringSerializer)；BFF 透传 body 用 rawBody 字符串。

## 5. 面试叙事点（规划期预埋）

1. **关注制触达设计**：主动提醒默认零推送——「错误不骚扰」从架构层保证（不是开关，是数据模型约束：无关注记录=无提醒）。
2. **历史价格采集的工程权衡**：每日全量快照 + 交易实时补点（下单/浏览写 point-in-time 价格），兼顾完整性与冷启动（新 SKU 无快照也有价格基线）。
3. **省钱汇总的组合正确性**：券实省（marketing 试算）+ 比价最优差（多 adapter）+ 降价已省（历史最低差）三个口径独立计算再合并，避免重复计入（同一笔不能既算券又算比价差）——口径即面试深度。
4. **实测数据**：采集任务耗时、检测任务吞吐、overview P95——压测可复现。

## 三、AI 售后管家 + Agent 定时购（P1）规划

> 立项背景：用户拍板「都做，先售后管家」——AI 售后管家先行，Agent 定时购作 P1 二期（复用一键代下单确认流）。
> 对齐红线：冷启动为零 / 第一屏可感知 / 错误不骚扰 / 用户价值 > 商家价值 > 技术叙事。

## 1. 现状盘点（不重复造轮子）

| 底座 | 状态 | 说明 |
|---|---|---|
| `aftersale_assistant(issue, aftersale_no)` | ✅ 已交付 | 售后话术生成 + 单号进度查询（aftersale-service） |
| `logistics_tracker(shipment_no)` | ✅ 已交付 | 物流轨迹 + 延误评估（logistics-service） |
| `after_sale_repair(action, order_no, ...)` | ✅ 已交付 | 质保盘点 + 维修预约（aftersale-service warranty/repair） |
| aftersale-service 接口 | ✅ 已交付 | `POST /aftersale/apply`（发起售后）/ `GET /mine` / `GET /{no}` / warranty / repair |
| H5 对话快捷入口 | ✅ 已交付 | 售后助手/物流管家卡片（chat/index.vue quickActs） |

**缺口**：①售后场景缺「聚合诊断」——一次查清「我的售后单 + 物流异常 + 质保到期」；②缺「一键发起售后」的 AI 入口（现有话术只提示到订单页手动发起）；③缺模型级确认门（防未确认执行，呼应本轮刚修复的「模型谎报执行」坑）。

## 2. 本轮开发块（A 块 · AI 售后管家工具）

### A1 新工具 `after_sale_manager(action, issue, order_no, type, reason, confirm)`

- **action=overview（默认）**：聚合三路诊断
  1. `GET /aftersale/mine?userId=` → 我的售后单（处理中/已完成）
  2. `GET /logistics/delay-alerts?userId=` → 物流延误预警（物流管家二期已有）
  3. `GET /aftersale/warranty/alerts?userId=&days=30` → 质保 30 天内到期/已过期
  → 输出「售后健康度」：N 单售后处理中、M 单物流异常、K 件质保临近 + 每项下一步建议（可追问详情）。
- **action=apply**：一键发起售后（**确认门**）
  - `confirm=false`（默认）→ 返回申请摘要 + 提示「回复『确认申请』后我立即提交」；**不执行任何写操作**（错误不骚扰红线）。
  - `confirm=true` → ① `GET order-service /{orderNo}` 取真实订单金额（**防编造金额**）→ ② `POST /aftersale/apply`（orderNo/type/reason/amount）→ 返回售后单号 + 状态。
  - 写操作带 `_http_post`（无重试，防重复创建）。

### A2 路由与提示词

- `system.md` 工具表追加 `after_sale_manager` 行（overview/apply + 确认门说明）。
- `_ROUTE_RULES` 新增售后管家触发词，**置于 aftersale_assistant 之前**（聚合优先）：
  `售后管家|处理售后|我的售后|售后情况|全部售后|售后汇总|我要退款|我要退货|我要换货|申请退款|帮我退款|物流卡住|快递没到|一直没到|催一下物流`

### A3 测试

- pytest 用例（mock _http_get/_http_post）：overview 三路聚合、空数据降级、apply 未确认不执行、apply 确认后真实提交（金额取订单服务）、坏参数友好降级。
- 真实链路验证（起 8090 aftersale + 8085 order）：造售后单 → overview 命中；apply 确认 → 售后单创建。

## 3. 后续块（P1 二期 · Agent 定时购，待拍板后开发）
