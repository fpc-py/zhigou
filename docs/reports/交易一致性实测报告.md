# 智购 · 交易一致性实测报告

> 项目：智购（Spring Cloud 微服务电商）
> 定位：简历深聊项目 · 交易链路可靠性验证
> 锚定价值：**买家不重复扣款、商家不超卖、状态不双写**——交易系统所有设计，最终都要回到这两个事实上。
> 测试方式：5 类真实故障注入（并发压测脚本），全部在真实运行的 6 服务（order/inventory/payment/product/cart/auth）上实测。
> 日期：2026-10-18 · 环境：Windows 本机 Docker 中间件（MySQL 8 REPEATABLE-READ / Redis 7 / RocketMQ 4.9）

---

## 一、为什么做这件事（面试第一句话）

电商交易系统的面试题，九成在问「你怎么保证不超卖」「你怎么保证幂等」「消息丢了怎么办」。做过项目的人都能说出「Redis 原子扣减」「唯一索引幂等」「outbox 模式」这些名词，但**名词是廉价的**——面试官真正想听的是：你知不知道这些方案**在真实并发下会怎么失败**、你怎么发现它失败的、失败后你怎么修、修完怎么证明修好了。

这份报告就是用**实测数据**回答这些问题的。5 个场景全部是真实故障注入（脚本见 `scripts/consistency-fault-injection/`），不是纸上谈兵。

交易链路（下单→扣库存→支付→关单/超时释放）：

## 四、深挖发现的真实 Bug 与修复全过程（本次最大收获）

### 场景 1 复现出的问题：并发幂等退化为 500

**现象（第一轮实测）**：30 并发同 requestId 下单。
- 数据正确：仅 1 单落库（唯一索引兜住了）
- 但 HTTP 结果：1×200 + **29×500**（DuplicateKeyException: `uk_user_request` 冲突）

这暴露的是「**先查后插**」幂等方案的经典竞态窗口：

```
请求A: selectOne(requestId) → 空 → insert ✓（提交）
请求B~D: selectOne(requestId) → 空（A 还没提交）→ insert ✗ 撞唯一索引
```

唯一索引确实是最后防线——数据没坏。但**兜底方式是抛 500**，等于把「重复点击」变成了「系统繁忙」。用户重试一次就多一次 500。这不是能上生产的代码。

### 修复尝试 1：catch + 回查 → 失败（REPEATABLE READ 快照读陷阱）

第一版修复：`insert` 外包 `catch(DuplicateKeyException)`，撞索引后幂等回查已存在订单并返回 200。

实测：29 个请求**确实进了 catch**（日志出现大量「重复下单(唯一索引兜底)」），回查查询也执行了，但**仍然 500**。

根因（用日志时间线钉死）：MySQL 隔离级别是 **REPEATABLE READ**（已查证 `@@global.transaction_isolation`）。在该隔离级别下，事务内**第一次 SELECT 建立一致性快照**，之后的普通 SELECT 都读这个旧快照：

```
请求B 事务开始 → selectOne(requestId)（快照建立，此时 A 未提交）→ insert 撞索引
→ catch 内 selectOne 回查 → 读的还是事务开始的旧快照 → 返回 null → rethrow → 500
```

**关键教训**：catch 内回查读到的不是「最新已提交数据」，而是「本事务第一次读时的快照」。数据明明在库里，就是读不到——这就是 REPEATABLE READ 快照读的隐蔽陷阱。

### 修复尝试 2：FOR UPDATE 当前读 → 失败（S→X 锁升级死锁）

第二版修复：回查 SQL 加 `FOR UPDATE`（当前读，绕过快照读）。

实测：200 从 1 → 23，但 28 个请求报 **DeadlockLoserDataAccessException**（死锁）。

根因：`INSERT` 撞唯一索引时，InnoDB 会让事务**持有冲突索引记录上的共享锁（S）**等待第一个事务提交；catch 里再 `SELECT ... FOR UPDATE` 需要把 S 升级为 **X 锁**（排他锁）——多个并发事务**互持 S 锁都想升级 X**，构成经典死锁，被 InnoDB 死锁检测随机击杀。

### 修复尝试 3：REQUIRES_NEW 独立事务 → 失败（连接池耗尽）

第三版修复：catch 内用 `REQUIRES_NEW` 开独立事务回查（新事务=新快照，且不参与原事务锁）。

实测：200 从 23 → 23，但 7 个请求报 **CannotCreateTransactionException: Could not open JDBC Connection**（连接池耗尽）。

根因：30 并发 ×（主事务 1 连接 + REQUIRES_NEW 1 连接）= 60 个连接需求，而 HikariCP 默认池只有 10。**REQUIRES_NEW 让连接占用翻倍**，高并发下直接打爆连接池——这也是生产上滥用 REQUIRES_NEW 的典型代价。

### 最终修复：READ COMMITTED（一个注解的正解）

第四版：`create` 事务显式降为 `@Transactional(isolation = READ_COMMITTED)`——该隔离级别下**每条语句重建快照**，catch 内普通 SELECT 就能读到最新已提交的并发订单。无锁、无额外连接、无死锁。

实测（最终数据）：
- **30 并发：30×200、0 错误、1 单落库、29 幂等返回、4.1s**（对比修复前：1×200 + 29×500、12.5s）
- **100 并发：100×200、0 错误、1 单落库、99 幂等返回、2.1s**

### 三次失败尝试汇总（面试最爱的部分）

| 方案 | 结果 | 失败根因 | 教训 |
|---|---|---|---|
| catch+快照读回查 | 29/30 仍 500 | REPEATABLE READ 快照读看不到刚提交的行 | 事务隔离级别决定「读得到什么」 |
| FOR UPDATE 当前读 | 28/30 死锁 | 唯一键冲突 S 锁 → X 锁升级互锁 | 锁读不是免费的，会引入死锁 |
| REQUIRES_NEW 独立事务 | 7/30 连接池耗尽 | 连接占用翻倍 > HikariCP 池 10 | 新事务放大并发资源需求 |
| **READ COMMITTED** | **30/30、100/100 全 200** | — | 读最新已提交+无锁的标准解 |

**面试怎么说**：幂等兜底不是「catch 一下就完」——要理解你在哪个隔离级别下读数据。我实测踩过三个坑（快照读、锁升级死锁、连接池耗尽），最终用「读最新已提交且不加锁」的 READ COMMITTED 落地，并有两组并发实测数据证明修复有效。

## 五、各场景实测细节

### 场景 1：并发幂等下单（30 / 100 并发）—— 见第四节，已闭环 ✅

### 场景 2：并发超卖（100 并发，库存 1 件）✅

- 注入：先把库存置 1（Redis），100 线程同时 `preDeduct(count=1)`
- 实现防御：`lua/deduct.lua` 单脚本原子 `get→compare→decrby`
- 实测：成功恰 1、失败 99（全部 40010 库存不足）、Redis 剩余 0、**0 超卖**、耗时 3.0s
- 说明：若 Lua 不是原子的（比如 GET 和 DECRBY 分开），100 并发下必然超卖——这正是为什么扣减必须在一个脚本里完成

### 场景 3：重复支付回调（30 并发同 paymentNo）✅

- 注入：完整链路下单→建支付单→30 并发同 paymentNo 调 mockPay（带签名）
- 实现防御：payment_no 唯一索引 + PENDING 才置 SUCCESS 的状态判断 + 通知幂等（notify_status 0→1）
- 实测：30×200、payment 表仅 1 条 SUCCESS（notify_status=1）、订单状态 PAID、**无重复入账**、耗时 2.9s

### 场景 4：outbox 双通道只释放一次 ✅

- 注入：下单→取消→等 35s（覆盖 OutboxDeliveryTask 30s 周期+MQ 消费）→ 同 orderId 重复 rollback×5
- 实现防御：`rollbackOrder` 用 Redis `SETNX inv:rb:{orderId}`（TTL 7 天）保证双通道只放行一次
- 实测：同步通道 +0、MQ 通道 +1、重复 5 次后仍 +1 → **累计释放恰 1**，SETNX 幂等成立
- **附带设计事实澄清**（写进报告当真相）：实测发现「用户取消」只走 ORDER_CLOSED MQ 单通道（+0 同步）；只有「超时关单」才是同步+MQ 双通道。单通道也安全（MQ at-least-once + 消费者幂等），但不是文档里说的双通道——这是设计事实，不是 bug，值得在面试里主动说清楚，展示你理解自己的系统。

### 场景 5：支付回调 vs 关单竞态（50 并发）✅

- 注入：INIT 订单上 50 并发=25 支付回调 + 25 取消
- 实现防御：状态机 `validateTransition`（PAID→CLOSED 非法，抛 40050）
- 实测：支付 25 全部成功、取消 25 全部被 40050 拦截、终态唯一 PAID、库存变化 0——**不会出现「已支付却被关闭」或「关闭后又支付」的状态双写**

## 六、结论与面试叙事要点

1. **数据证明底线成立**：5 类真实故障注入，全部守住「买家不重复扣款、商家不超卖」。
2. **最大的收获不是方案，而是失败路径**：并发幂等兜底三次修复失败的根因（快照读 / 锁升级死锁 / 连接池耗尽）是任何教科书都不会写给你的，而面试官最想听的就是这种「我踩过、我懂为什么、我修对了、我有数据」的故事。
3. **方案选型原则**（可复用判断）：需要读「最新已提交 + 不加锁」→ 用 READ COMMITTED 或新连接；需要「加锁串行化」→ 锁读（但要防死锁）；需要「跨事务隔离」→ REQUIRES_NEW（但要防连接池翻倍）。
4. **对用户的价值**：这些防御最终都回到买家（不重复扣款、不白关单）和商家（不超卖、不重复释放库存）身上——技术不是炫技。
