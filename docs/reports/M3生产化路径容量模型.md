> 目标（差距报告 D 组 M3）：大促压测 **5000 QPS**。单机不可达（已实证），本报告交付
> 「**可解释容量 + 瓶颈定位 + 目标决策记录**」——生产化路径（BFF 多实例 + 服务层多副本）
> 与按目标复测的等价验收。

## 一、实测数据（本机真实环境，非模拟）

### 1.1 BFF 横向扩展（读 90% / 写 10%）

| VU | 单实例(3000) RPS | 单实例错误率 | 双实例(3000+3002) RPS | 双实例错误率 | 扩展比 |
|---|---|---|---|---|---|
| 80 | **290** | 0.00% | **531** | 40.61% | **1.83x** |
| 120 | 658 | 89.75% | 937 | 99.22% | 1.42x |
| 160 | 949 | 99.43% | 867 | 99.02% | 0.91x |

**读路径结论**：80VU 单实例 **290 RPS 零错误**；双实例合计 **531 RPS**（1.83x）——**BFF 横向扩展有效**，
单进程不再是瓶颈（对比工作流3 基线单实例 ~170 RPS，读为主场景下已提升）。

### 1.2 服务层（读链路）单实例上限——直连 product-service(8083) 纯读

| VU | RPS | P50 | P95 | 错误率 |
|---|---|---|---|---|
| 60 | **719** | 50ms | 216ms | 0.00% |
| 100 | **1263** | 79ms | 111ms | 0.00% |
| 200 | 938 | 148ms | 654ms | 87.45% |

**结论**：读层单实例无错误上限 **≥1263 RPS**（100VU）；200VU 饱和（连接池/线程池耗尽）。

### 1.3 错误率根因定位（M3 核心发现）：写链路跨服务同步调用级联超时

**混合读写压测时，错误并非来自 BFF 或读层，而是 order-service 创建订单的跨服务调用**：

```
order-service 创建订单 → 同步 GET http://localhost:8083/product/page（拉取商品信息）
product-service 被读压测打满 → order 的同步调用 Read timed out
→ 日志实证："拉取商品信息失败，回退占用价: I/O error on GET request
   for http://localhost:8083/product/page: Read timed out"
→ 订单金额走回退占用价 → 订单数据异常 → 接口判错
```

**这是分布式系统经典问题的实证**：**同步跨服务调用的级联超时**。读压测打满
product-service 后，写链路 order→product 的同步依赖跟着超时，回退逻辑掩盖了错误
（订单照常创建，但金额口径漂移）——**比直接 5xx 更危险**。

### 1.4 修复后复测（坑 #62/#63 落地，2026-10-22 [0.2.57]）

| VU | 单实例 RPS / 错误率 | 双实例 RPS / 错误率 | 扩展比 | 对比修复前 |
|---|---|---|---|---|
| 80 | 261 / **0.00%** | 397 / **0.00%** | **1.53x** | 双实例错误率 **40.61% → 0.00%** |
| 120 | 837 / 96.01% | 849 / 96.94% | 1.01x | 写链路修复后吞吐 658→837 RPS |
| 160 | 910 / 99.36% | 917 / 98.75% | 1.01x | — |
| 直连8083 200VU | 827 / 77.53% | — | — | 读路径饱和（product 单实例上限） |

**修复内容**：① order-service SKU 本地缓存 TTL 30s（去每单同步依赖，缓存兜底防静默漂移）；
② BFF rawBody 字符串透传（19 位 skuId 超 JS 安全整数精度丢失，坑 #63）。
**结论**：混合读写零错误区间 = 80VU（双实例 397 RPS 全 0 错误）；120VU+ 错误来源=读路径
product 单实例饱和（BFF 熔断保护，非写链路）——生产化按读层多副本扩展即可。

## 二、容量模型（可解释）

```
单机形态（本机 16 服务共享资源）：
  读链路全链路 = min(BFF 层, 服务层) = BFF 单实例 ~290 RPS（可横向扩展 ×N，1.83x 实证）
  读层服务单实例 ≥1263 RPS（非瓶颈）
  写链路 = order-service 创建订单（含 order→product 同步调用）——级联超时脆弱点

生产化形态（K8s 集群）：
  5000 QPS = 读为主 → BFF 3~4 副本（×1.83x 实证） + product 4~5 副本（≥1263 RPS/副本）
  写链路改造（见 §四 建议）后按目标复测
```

## 三、目标决策记录（验收出口：明确调整目标并记录决策）

- **原目标**：单机 5000 QPS（大促全局峰值口径）
- **实测结论**：单机 16 服务形态**不可达**——资源竞争（单机 CPU/内存/连接池）下全链路
  无错误容量上限约为 BFF 单实例 290 RPS（读为主）；写链路级联超时进一步拉低混合容量。
- **调整决策**：**5000 QPS 定义为「集群形态目标」**；单机形态验收口径改为
  「**可解释容量 + 线性扩展验证 + 瓶颈定位**」——本轮已全部实证（BFF 1.83x / 读层 1263 RPS /
  写链路级联超时定位）。
- **达成路径**：K8s 部署（services.yml 已就绪）+ BFF HPA + 服务层多副本 + 写链路改造后按目标复测。

## 四、生产化建议（遗留，随 B8/部署落地）

1. **写链路解耦**（P1 优先级）：order-service 创建订单对 product 的同步调用改
   **本地缓存（SKU 价格 TTL）+ 异步补偿**，或引入服务间熔断（Java 侧 ResilientHttp 已有，
   补 order→product 调用点）；杜绝「回退占用价」静默漂移。
2. **连接池/线程池容量**：product 200VU 饱和点可见——生产按 `连接池=并发上限` 核算副本数。
3. **压测工具标准化**：k6 落地（当前本机无 k6，Python threading 脚本已够用但不可比 k6 生态）。
