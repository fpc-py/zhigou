## 一、#10 traceId 全链路（已完成）

### 1.1 解决的问题

16 个微服务 + BFF + AI 编排，跨服务排障时"日志散落各服务、无法串成一条请求链路"。
下单 → 扣库存 → 通知支付 → 售后，一次用户操作会横跨 3~5 个服务，某个环节慢/挂，
需要人工按时间戳拼日志才能定位。

### 1.2 怎么做

公共库（`packages/common`）新增 `trace` 包，三个透传点 + 两个自动配置：

| 组件 | 职责 |
|---|---|
| `TraceIdFilter` | 入站过滤器（`OncePerRequestFilter`，`@Order(HIGHEST_PRECEDENCE)`）：读 `x-trace-id` 头，无则生成 12 位 UUID → 写入 MDC（key=`traceId`）→ 响应头回写 → `finally` 清理 MDC（防线程池复用串线） |
| `TraceIdClientHttpRequestInterceptor` | RestTemplate 出站拦截器：MDC → `x-trace-id` 请求头，下游服务复用同一 traceId |
| `TraceIdFeignRequestInterceptor` | OpenFeign 出站拦截器：同上（Feign 自动收集所有 `RequestInterceptor` bean） |
| `TraceAutoConfiguration` | 注册 TraceIdFilter（无 feign 引用） |
| `TraceFeignAutoConfiguration` | 注册 Feign 拦截器，`@ConditionalOnClass(EnableFeignClients.class)` 按需装配 |

11 个服务 `application-dev.yml` 日志 pattern 带 `%X{traceId}`；
本服务实际输出为 JSON 结构化日志（logstash 风格），MDC 自动落为顶层 `traceId` 字段。

### 1.3 实测数据（故障注入）

带自定义 traceId 走完整下单链路（order → product 跨服务调用）：

```
curl -X POST http://localhost:8085/order/create \
  -H "x-trace-id: TRACETEST123456" -H "x-user-id: 10001" \
  --data-binary @body.json

order(8085)  日志: "traceId":"TRACETEST123456"   ← 入站注入
product(8083) 日志: "traceId":"TRACETEST123456"  ← RestTemplate 透传
```

**结论**：同一 traceId 贯穿 order → product 两个服务，日志按 traceId 过滤即可还原整条调用链。

### 1.4 踩过的坑（面试素材）

| 坑 | 现象 | 根因 | 解决 |
|---|---|---|---|
| optional 依赖不传递 | product 启动 `NoClassDefFoundError: feign/RequestInterceptor`，上下文初始化中断 | 公共库 openfeign 是 `<optional>true</optional>`（避免强制下游携带），optional 依赖**不传递**；自动配置类方法签名引用 feign 类型 → 无 Feign 服务类加载即炸 | 拆 `TraceFeignAutoConfiguration` 独立类 + `@ConditionalOnClass`，按需装配（bug #38） |
| RestTemplate 构造器重载 | 想用 `new RestTemplate(factory, interceptors)` 注入拦截器 | RestTemplate 无该双参构造器 | 改用 `restTemplate.setInterceptors(List.of(...))`，保留各服务超时配置 |
| PowerShell 传 JSON body | `curl -d '{"a":1}'` 引号被吞 → JSON parse error | Windows 命令行引号传递 | `--data-binary @file.json`（文件无 BOM UTF-8） |

## 二、#7 服务间超时/熔断（已完成）

### 2.1 解决的问题

服务间调用裸奔：order→product、order→inventory、cart→product、payment→order 共 4 处，
只有 RestTemplate 超时（300ms~1000ms），**下游故障时每个请求都要等满超时**，
无快速失败、无状态隔离——一个服务抖动会拖垮整条链路（雪崩前兆）。

### 2.2 怎么做

公共库新增 `ResilientHttp`（编程式熔断执行器）+ resilience4j-spring-boot3（传递全部服务）：

```java
// 调用点改造（order fetchSkuInfo）
ResponseEntity<String> resp = resilientHttp.execute("orderFetchSku",
        () -> restTemplate.exchange(url, HttpMethod.GET, entity, String.class));
// 失败抛异常 → 既有 catch 降级逻辑接住（占位价 100），业务不中断
```

配置（三个服务 application.yml 统一参数化）：

```yaml
resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-size: 10          # 滑动窗口 10 次
        failure-rate-threshold: 50       # 失败率阈值 50%
        slow-call-duration-threshold: 2000ms
        slow-call-rate-threshold: 50
        wait-duration-in-open-state: 10s # 打开 10s 后自动半开
        permitted-number-of-calls-in-half-open-state: 3
        automatic-transition-from-open-to-half-open-enabled: true
    instances:
      orderFetchSku: { base-config: default }
      orderReleaseInventory: { base-config: default }
      cartValidateSku: { base-config: default }
      paymentNotifyOrder: { base-config: default }
```

**为什么用编程式而非 @CircuitBreaker 注解**（重要坑）：
Resilience4j 注解走 Spring AOP 代理，**同类 private 方法 self-invocation 不经过代理 → 熔断失效**。
本项目 4 个调用点全部是同类私有方法，注解方案需提 public + 自注入代理（侵入大），
编程式 `registry.circuitBreaker(name).executeSupplier(call)` 无代理依赖、private 可用、fallback 即既有 catch。

可观测：`ResilientHttp` 为每个熔断器注册状态变迁事件日志
（`[熔断] orderFetchSku 状态变化: CLOSED → OPEN`），排障与告警埋点基础（#8 的输入）。

### 2.3 实测数据（故障注入：杀 product 进程）

| 阶段 | 观测点 | 数据 |
|---|---|---|
| 正常 | 下单金额 | **9900**（真实价，熔断 CLOSED） |
| 故障注入 | taskkill product 进程 | 12 连发下单，失败率 100% > 50% 阈值 |
| 熔断触发 | 事件日志 | `[熔断] orderFetchSku 状态变化: CLOSED → OPEN` |
| 熔断拦截 | 失败日志 | `CircuitBreaker 'orderFetchSku' is OPEN and does not permit further calls`（**未发起网络调用**） |
| 业务降级 | 订单金额序列 | 9900 → **100×N**（占位价下单，订单照常创建、用户无感知异常） |
| 半开探活 | 事件日志 | `OPEN → HALF_OPEN` → `HALF_OPEN → OPEN`（探活失败自动重开） |
| 自动恢复 | 下单金额 | **9900**（product 恢复，半开探活成功 → CLOSED，耗时 310ms） |

**结论**：
1. 熔断触发后失败从"等满网络超时"变为"毫秒级快速失败"（不占线程）；
2. 下游故障期间**核心交易不中断**（占位价降级 + 对账兜底，见工作流1）；
3. 恢复零人工干预（10s 后自动半开探活，成功即关闭）。

### 2.4 踩过的坑（面试素材）

| 坑 | 现象 | 根因 | 解决 |
|---|---|---|---|
| 注解熔断对 private 方法失效 | @CircuitBreaker 加在 private 方法无效果 | AOP 代理不拦 self-invocation | 编程式 `CircuitBreakerRegistry`（本报告 2.2） |
| final 字段无构造器注入 | payment 编译失败"变量未在默认构造函数中初始化" | `@Component` 类加 `private final` 字段但无 `@RequiredArgsConstructor` | 补 Lombok `@RequiredArgsConstructor` |
| jar 被进程锁 | maven repackage "Unable to rename ...jar.original" | Windows 上运行中 java 进程锁住 jar 文件 | 先停服务再打包（部署脚本化） |
| PowerShell 搜中文日志 | Select-String 匹配"订单创建"为 0 | PS 5.1 默认 ANSI 解码 UTF-8 文件 | 实测断言改用 python utf-8 读取日志 |

## 三、#9 全链路压测 + 瓶颈定位（已完成）

### 3.1 压测设计与方法

- **工具**：本机无 k6，自研 Python threading 压测器 `scripts/load-test/test_chain_load.py`（真并发，非 asyncio+同步阻塞假并发）。
- **黄金路径**：读 80% `GET /product/page?pageNum=1&pageSize=10` + 写 20% `POST /order/create`（requestId 唯一幂等）。
- **分层对比法（瓶颈定位）**：同一并发档位分别打 **BFF(3000) 入口** 与 **直连服务**（product 8083 / order 8085），
  对比 RPS/RT 差异 → 定位瓶颈在"转发层"还是"服务层"（prometheus 端点被安全链 403 拦截，故用分层对比替代指标采样）。
- **档位**：50 / 100 / 200 VU × 20s，JWT 自签（HS256，sub=13800138000）。

### 3.2 实测数据（修正后，零误判）

| VU | BFF RPS | BFF P50/P95/P99 | 直连 RPS | 直连 P50/P95/P99 | RPS 差 |
|---|---|---|---|---|---|
| 50 | **173** | 258 / 534 / 943ms | 177 | 16 / 1696 / 2490ms | -2% |
| 100 | **137** | 694 / 1083 / 1250ms | 381 | 39 / 1297 / 1748ms | -64% |
| 200 | **114** | 1624 / 2631 / 2838ms | 375 | 46 / 2553 / 2888ms | -70% |

全部档位**错误率 0.00%**（除 200VU 直连 0.41%，为下单库存瞬时竞态，见 3.3 坑）。

### 3.3 关键坑（面试素材，差点被误导）

| 坑 | 现象 | 根因 | 解决 |
|---|---|---|---|
| **压测器把 201 当错误** | 初版数据"BFF 错误率 19.46%"差点得出"BFF 有 19% 故障"的**错误结论** | BFF 写路径返回 **201 Created**（Nest 默认 POST 状态码），断言只认 200 → 20% 写请求全被误判失败 | 判定改为 `200/201` 均成功；分路径采样确认（写 201×1800、读 200×2400、混合 200×1772+201×415 全零错误） |
| asyncio+同步 urllib 假并发 | 压测器第一版跑 20 分钟只出预热 | urllib 同步阻塞调用拖死 event loop，并发被串行化 | 重写 threading 真并发（每 VU 一线程） |
| 200VU 直连 0.41% 错误 | 偶发下单失败 | 同一 SKU 高并发下的库存扣减瞬时竞态（乐观锁重试窗口） | 记录为已知限制：写路径并发压测应使用多 SKU 摊开热点 |

### 3.4 瓶颈定位结论（可解释容量，替代拍脑袋的 5000 QPS）

1. **系统本身 0 错误、可靠**（修正统计后）——"19% 故障"是压测断言坑，不是系统故障；
2. **容量天花板 = BFF 转发层（单实例）**：并发 50→200VU，BFF RPS 不升反降（173→137→114），P50 线性恶化（258→694→1624ms = 排队效应）；**直连服务层稳定 375~381 RPS、P50 <50ms**——Java 服务 + MySQL 不是瓶颈；
3. **可解释容量**：本机单实例部署下，**服务层稳定容量 >370 RPS（P50 <50ms）**，BFF 单实例有效容量约 **170 RPS**（再加压只会排队变慢，不会崩）；
4. **扩容方向（数据支撑，非猜测）**：BFF 横向多实例（无状态、鉴权在 guard、无本地 session）+ 下游 keep-alive 连接池调优，收益远大于加 Java 服务节点。

### 3.5 落地验证：BFF 横向多实例扩展（2026-10-19，[0.2.39]）

压测结论的落地动作：起第 2 个 BFF 实例（`PORT=3002 node dist/main.js`），用 `scripts/load-test/test_bff_scale.py`（200VU 轮询分发到 3000/3002 = 负载均衡模拟）与单实例基线对比。

| 档位 | 单实例 RPS | 双实例 RPS | 扩展比 | 单 P50 | 双 P50 | 错误率 |
|---|---|---|---|---|---|---|
| 100VU | 97 | **184** | **1.89x** | 888ms | 465ms | 0.00% |
| 200VU | 74 | 115 | 1.55x | 2708ms | 1678ms | 0.00% |
| 300VU | 100 | 118 | 1.18x | 2737ms | 2435ms | 0.00% |

**结论**：① 100VU 下双实例吞吐 **1.89x≈线性**、P50 减半——**瓶颈确认为 BFF 单进程（Node 单线程事件循环），横向多实例有效**；② 200/300VU 扩展比回落（1.55/1.18x）且 P50 飙升，是**本机整体负载**所致（16 个 Java 服务 + Docker Desktop + 2×Node 同机并行），非服务层瓶颈（服务层独立基线 >370 RPS）；③ 实测中再次踩坑：**压测 token 过期 → 全量 401 → 错误率 100% 的假数据**，修复后 0 错误率（见 bug #42）。

**扩容结论**：BFF 按 ~2×单实例有效容量横向扩展（本机单实例有效容量受负载波动在 100-170 RPS 区间，生产按 2 实例起步、每实例独立部署 + 前置负载均衡轮询），Java 服务层容量充足暂不扩。
## 四、#8 告警接入（已完成）

### 4.1 解决的问题

熔断/超时/高错误率"发生了才知道"——无主动告警。故障注入实测中熔断 OPEN 只能靠翻日志。

### 4.2 怎么做

| 资产 | 内容 |
|---|---|
| **14 个服务 SecurityConfig 放行 `/actuator/prometheus`** | 修复 prometheus 端点 403（安全链只放行 health）；只放行指标端点，不开放 env/beans |
| **`conf/prometheus/alerts.yml`（5 条规则）** | `CircuitBreakerOpen`（OPEN>1min critical）/ `CircuitBreakerFlapping`（半开反复探活）/ `HighErrorRate`（5xx>5% 2min）/ `HighLatencyP95`（P95>2s 2min）/ `ServiceDown`（实例掉线 1min） |
| **`conf/prometheus/alertmanager.yml`** | 告警路由：critical/warning 分级通道（webhook 占位，接入钉钉/飞书即用）+ critical 抑制 warning |
| **`prometheus.yml` 挂载 rule_files + alerting** | Prometheus → Alertmanager 告警链 |
| **monitoring.yml 编排** | 新增 alertmanager 服务（9093）+ alerts.yml 挂载，compose config 校验通过 |
| **熔断事件日志埋点**（工作流3 #7 已交付） | `[熔断] orderFetchSku 状态变化: CLOSED → OPEN`，日志侧告警输入 |

### 4.3 实测数据

| 验证项 | 结果 |
|---|---|
| 4 个核心服务 `/actuator/prometheus` | **全部 HTTP=200**（修复前 403） |
| 熔断指标暴露 | `resilience4j_circuitbreaker_state{application="payment-service",name="paymentNotifyOrder",state="closed"} 1.0` 等，4 个调用点指标齐全 |
| 告警规则语法 | `promtool check rules` → **SUCCESS: 5 rules found** |
| compose 配置 | `docker compose config --quiet` → **EXIT=0** |

**闭环链路**：下游故障 → 熔断 OPEN → 状态指标 `resilience4j_circuitbreaker_state{state="open"}` → Prometheus 每 15s 抓取 → 规则评估 1min → Alertmanager 分级告警（webhook/钉钉/飞书）→ 值班人凭 traceId 日志定位。

### 4.4 踩过的坑（面试素材）

| 坑 | 现象 | 根因 | 解决 |
|---|---|---|---|
| actuator 端点 403 | `/actuator/prometheus` 403，Prometheus 无数据源 | Spring Security 只放行 `/actuator/health`，anyRequest().authenticated() 拦住指标端点 | 各服务 SecurityConfig 显式放行 `/actuator/prometheus`（最小暴露原则：不放行整个 actuator） |
| compose up 卡住 | `docker compose up -d` 无输出卡死 | 本机 Docker Desktop 资源/拉取与容器创建慢（配置本身 promtool 与 compose config 均校验通过） | 验证用 promtool 单容器（`--entrypoint promtool`，注意新版 prom/prometheus 镜像入口已非 promtool，需指定 v3.13.3）；编排 up 待 Docker Desktop 环境正常时执行 |
