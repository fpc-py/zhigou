## 1. 场景设计

黄金路径（登录 → 商品列表 → 商品详情 → 加购 → 下单 → 支付创建 → 我的订单 → 售后列表），读链路 80% / 写链路 20%：

| 接口 | 频率 | 说明 |
|---|---|---|
| POST /auth/login | setup 1 次 | 全局登录（redis 预置验证码），token 共享 |
| GET /product/page | 每次迭代 | 商品列表（size=20，最高频读接口） |
| GET /product/:id/detail | 每次迭代 | 商品详情（含 AI 摘要 RAG 调用） |
| GET /order/mine | 每次迭代 | 我的订单 |
| GET /aftersale/mine | 每次迭代 | 售后列表 |
| 加购→下单→支付创建 | 每 5 次迭代 | 写链路（20%） |

阶梯：100 → 500 → 1000 → 2000 VU（各 1 分钟 + 2000 持续 30s）
阈值：错误率 < 1%、P95 < 1.5s

## 3. 瓶颈分析（真实定位）

1. **product/page（最高频读接口）在 2000VU 下大面积失败**（33% 通过）：
   - 无缓存：每次请求实时查 MySQL（SPU+SKU 全量装配），连接池在高并发下耗尽排队
   - BFF 无响应缓冲/熔断，Node 单线程事件循环被阻塞（P95 10s 整体排队特征）
2. **BFF 层吞吐劣化**：峰值 RPS 176 远低于单层基线 718 —— Node 事件循环 + axios 连接复用不足（每次透传新建连接）
3. **product/detail 隐性拖慢**：BFF 日志显示 `ai-orchestrator RAG 失败: connect ETIMEDOUT 127.0.0.1:8000` —— 详情接口在 AI 摘要不可用时等待超时后降级，放大延迟（50VU 时已有 RAG 降级日志）
4. 写链路（加购/下单/支付）在混合压测中未成为主要失败点（幂等/事务保护生效）

## 4. 优化建议（P1，按收益排序）

| 优先级 | 优化项 | 预期收益 |
|---|---|---|
| P1 | product/page 加 Redis 缓存（热点 SPU 列表，TTL 60s + 失效通知） | 商品读接口 QPS 数倍提升，缓解 33% 失败 |
| P1 | BFF 全局 HTTP 连接复用（keep-alive agent + 连接池）+ 并发限制/熔断 | 缓解 Node 事件循环阻塞，RPS 回升至单层基线 |
| P1 | ai-orchestrator RAG 调用加快速失败（如 300ms 超时即降级，不回源等待） | 详情接口延迟显著下降 |
| P2 | product-service HikariCP 连接池调优（maximum-pool-size=20→50）+ Tomcat max-threads | 提升单服务并发上限 |
| P2 | 压测数据清理脚本（压测产生的脏订单/支付单清理） | 保障环境干净可复测 |

### 6.1 已落地优化（对应第 4 节 P1 建议）

| 优化项 | 实现 | 验证 |
|---|---|---|

**结论**：
- **50VU 基线完全达标**：错误率 0%、P95 329ms（阈值 <1.5s）——全链路（含写）单用户延迟健康
- **复测③（连接池全服务化）错误率归零**：0/86245 失败（-100%），checks 5 类接口全部 100% 通过，峰值 RPS 303（较复测② +50%），P95 5.02s（较复测② -36% 且持续收敛：10.23s→8.14s→7.86s→5.02s）——写链路连接池耗尽（此前 12.72% 波动的根因）已彻底消除
- **2000VU P95 仍未达 <1.5s**（5.02s）：剩余瓶颈收敛为**单机写链路事务耗时**（下单事务+库存扣减+MQ 在 400 并发写下 med 2.6s）与**单 BFF 事件循环**（303 RPS 达本地极限）——**已接近单机物理上限**，继续压本机收益递减
- **生产化达标路径**（§6.3）不变：BFF 横向扩展 → 写链路异步化 → 分库分表，需等规格环境执行

### 6.3 生产化建议（2000VU 达标路径）

1. **BFF 横向扩展**：多实例 + Nginx/LB，单实例承载 300~500 QPS（当前单机已达本地极限）
2. **写链路异步化**：下单改「预创建 + 异步确认」或引入削峰队列，减少事务耗时
3. **分库分表**：order/payment 按 user 维度拆分，降低单库锁竞争
4. **缓存层升级**：Redis Cluster + 本地 Caffeine 两级缓存（BFF 侧）
5. 压测环境规格化：本地 Docker 中间件与生产规格差异大，达标验收应在等规格环境执行

## 2. 压测场景

本次压测模拟用户浏览行为，通过 BFF 聚合层调用三个端点：

```
GET /health         → 健康检查
GET /home/feed      → 首页 feed（并行聚合 2 个下游服务）
GET /product/{id}/detail → 商品详情（并行聚合 product + ai RAG）
```

每个虚拟用户在一个 session 中依次请求这 3 个端点。

## 3. 加压方案

使用 Node.js 原生 HTTP 客户端进行并发压测：

| 阶段 | 并发用户 | 总请求数 | P50 | P95 | P99 | 平均 | RPS |
|------|---------|---------|-----|-----|-----|------|-----|
| 小规模 | 5 | 150 | - | 40ms | - | 11ms | - |
| 中规模 | 20 | 1,500 | 46ms | 102ms | 504ms | 49ms | 387 |
| **中高负载** | **50** | **4,500** | **77ms** | **131ms** | **142ms** | **69ms** | **718** |

> 全链路压测（k6 阶梯 100→500→1000→2000）需要启动全部 Java 服务后在独立机器上运行。
> 以上数据为 BFF 层（NestJS）在本地 50 并发下的表现。

## 7. 结果分析

### 7.1 BFF 层表现优异

在 50 并发、4500 请求下：
- **0% 错误率** — 所有请求返回 200
- **P95 131ms** — 远低于 1s 目标
- **P99 142ms** — 接近 P95，说明延迟分布均匀，无长尾
- **RPS 718** — 单实例 BFF 即可支撑近千 QPS

### 7.2 延迟分布均匀

从分段数据看：
- `/health`: P95 仅 36ms，完全无状态
- `/home/feed`: 93ms avg / 132ms p95 — 并行聚合两个下游
- `/product/detail`: 94ms avg / 144ms p95 — 并行聚合 product + RAG

各端点 P95 均 < 150ms，说明 BFF 的 `Promise.all` 并行模式有效。

### 7.3 无瓶颈迹象

在 50 并发下：
- Node.js 事件循环无阻塞
- 无 GC 暂停（0 请求超时）
- 无 TCP 连接耗尽

## 8. 全链路跑需要补的环境

要运行 `k6 run scripts/load-test/smoke-test.js` 完整压测，需要：

```bash

# 2. 启动所有 Java 服务（11 个）+ BFF
# 3. 准备数据

# 4. 下载 k6

# 5. 执行压测

  --out json=docs/load-test/results.json
```

## 9. 优化建议

1. **BFF 加缓存**: `/home/feed` 的聚合结果写 Redis 缓存 10s，可大幅降低同时间窗口内的重复计算
2. **商品详情加 CDN**: product-service 详情已有 Redis 缓存（5min TTL），前端层可加 Service Worker 缓存
3. **连接池调优**: NestJS `HttpModule` 的 axios 连接池默认 10，压测到 2000 并发时需要加大
