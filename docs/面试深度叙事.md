# 智购 · 面试深度叙事（简历项目可深聊清单）

> 定位：简历项目"能深聊"的话术沉淀。每条叙事 = 背景（真实问题）→ 怎么做 → **实测数据** → 面试官追问怎么答。
> 原则：不罗列技术名词，讲"用 X 解决了什么问题、怎么做、效果如何"。数据全部来自本机真实故障注入/压测（2026-10-18），可复现。

---

## 一、交易一致性：隔离级别从 REPEATABLE READ 到 READ COMMITTED

### 讲什么（60 秒版本）

**背景**：下单链路涉及订单表 + 库存扣减 + 支付回调三方，并发压测一上来就死锁/超时。
**怎么做**：不是拍脑袋改，而是写了 5 个故障注入场景逐个打（幂等重复下单、并发扣库存、超时关单、支付对账补偿、状态机非法跃迁），用数据定位。
**坑**：默认 REPEATABLE READ 下，并发事务先快照读后 UPDATE，MySQL 行锁 + 间隙锁互相等待 → 死锁（`Deadlock found` 实测复现）；改成 REQUIRES_NEW 传播又导致嵌套事务连接池耗尽；**最终 READ COMMITTED + 显式 FOR UPDATE**——只锁要写的行，不加间隙锁。
**数据**：修复后 30 并发下单 **0 错误 / 每单仅 1 次扣减 / 4.1s 完成**（修复前死锁率 ~9%）。
**附带**：requestId 唯一索引做幂等（重复点击/重试不会重复下单）、支付回调按 payment_no 幂等、超时订单定时关单+库存回补走对账兜底。

### 面试官怎么问、你怎么接

| 追问 | 应答要点 |
|---|---|
| 为什么不用悲观锁/分布式锁？ | 单库场景行锁足够，悲观锁会把读也串行化；关键在**锁的粒度**——FOR UPDATE 只锁写行，配合 RC 消除间隙锁 |
| 幂等怎么做？ | DB 唯一索引 + 冲突兜底（`INSERT IGNORE`/捕获 DuplicateKey），比 Redis 布隆过滤器更可靠（持久化） |
| 关单和支付并发到达怎么办？ | 状态机显式 transition map 校验（INIT→PAID/CLOSED 二选一），非法跃迁抛业务码 40050，先到先得 |
| 为什么不直接上分布式事务（Seata/TCC）？ | 交易链路 2PC 太重、性能差；最终一致性（outbox + 对账）在电商场景更务实——**用对账兜底换可用性** |

## 二、AI 链路工程化：工具可靠性 + 防编造 + RAG 检索质量 + SSE 连接管理

### 讲什么（90 秒版本）

**背景**：AI 智能体调工具下单/查库存，LLM 幻觉 + 工具超时会让用户看到"假商品/假库存"。
**四块深挖**：
1. **工具可靠性**：统一 timeout/retries 封装。**读操作幂等可重试（只重试 5xx，不重试 4xx）**；**写操作（下单）绝不自动重试**——重试 = 重复下单，宁可让用户手动重试。
2. **防编造**：工具结果进 LLM 上下文前过"关键词表 + 强制护栏"（必须引用真实工具返回字段，商品卡只能来自搜索结果）。
3. **RAG 检索质量**：踩到真实 bug——pgvector **ivfflat 索引在小数据集上退化**（lists 数 > 行数，召回率掉到 ~80%）；换 **HNSW + min_score 0.50 阈值**后 100% 命中。
4. **SSE 连接管理**：前端 sse-polyfill 重写——断链**指数退避 1/2/4/8s + 最多重连 4 次**、**30s 无数据判定假死主动释放**、**幂等续传**（断点后不重复渲染已收到的 token）。

### 实测数据

- 工具故障注入：模拟 5xx/超时/网络异常 → 读幂等重试成功、写不重试（防重复下单验证：并发双击只产生 1 单）
- 防编造：注入"编造商品"样本 → 护栏拦截率 100%
- RAG：ivfflat → HNSW 后 **100% 命中**（min_score 0.50）
- SSE：断网 → 指数退避重连恢复；杀进程 → 30s 假死释放

### 面试官怎么问、你怎么接

| 追问 | 应答要点 |
|---|---|
| 为什么 4xx 不重试？ | 4xx 是请求本身问题（参数/鉴权），重试 100 次结果一样还浪费资源；5xx 是服务端瞬时故障，重试有效 |
| 写操作不重试，丢单怎么办？ | 用户可见的失败 → 前端提示重试；真正防的是**静默重复下单**。配合 requestId 幂等，用户重试也安全 |
| 防编造是硬规则还是软约束？ | 双层：硬护栏（工具结果必须来自真实调用）+ 提示词约束（不得编造未返回字段）；LLM 输出还会做关键词校验 |
| ivfflat 为什么在小数据上退化？ | ivfflat 是倒排聚类，lists 太大时每个列表只有几条记录，probe 命中的列表覆盖不了全部数据；HNSW 是图索引，小数据也稳定 |

## 三、traceId 全链路：日志贯穿 16 个服务

### 讲什么（45 秒版本）

**背景**：下单横跨 order→product→inventory 等 5+ 服务，排障靠人工拼时间戳。
**怎么做**：公共库 trace 包——入站 Filter 生成/透传 `x-trace-id` 写 MDC，RestTemplate/Feign 出站拦截器自动带下游，响应头回写前端；11 个服务日志 pattern 统一打 `%X{traceId}`。
**坑**（真实踩到）：公共库 openfeign 是 `<optional>true</optional>` **依赖不传递** → 无 Feign 服务启动直接 `NoClassDefFoundError: feign/RequestInterceptor` 崩掉 → 拆独立自动配置 + `@ConditionalOnClass` 条件装配修复。
**数据**：带 `x-trace-id: TRACETEST123456` 下单 → order(8085) 与 product(8083) 日志 traceId 完全一致，跨服务链路一条命令还原。

### 面试官怎么问、你怎么接

| 追问 | 应答要点 |
|---|---|
| 为什么不直接用 SkyWalking？ | 项目要可移植、可演示，不引重量级 APM；自研 3 个组件 100 行内搞定，且完全兼容 Spring Boot 3 / WebFlux 以外的同步栈 |
| MDC 会串线吗？ | 会！线程池复用线程时 MDC 残留上一请求 traceId → 入站 Filter `finally` 清理 MDC（实测过串线场景才加的） |
| optional 依赖的坑能展开吗？ | 公共库把 feign 设 optional 是为了不强制下游带 feign；结果自动配置类方法签名引用了 feign 类型，无 feign 的类加载直接 NoClassDef → 教训：**自动配置必须按需装配（@ConditionalOnClass），不能裸引用 optional 依赖的类型** |

## 四、服务间熔断：注解失效，编程式接管

### 讲什么（60 秒版本）

**背景**：order→product 等服务间调用裸奔，下游挂了每个请求要等满网络超时，一个服务抖动拖垮整条链路。
**怎么做**：公共库 ResilientHttp 编程式熔断（resilience4j）包住 4 个调用点；参数统一（滑动窗口 10、失败率 50%、慢调用 2s/50%、打开 10s 自动半开、半开 3 次探活）；状态变迁打事件日志。
**坑**：**@CircuitBreaker 注解对同类 private 方法完全失效**——注解走 Spring AOP 代理，self-invocation 绕过代理（@Transactional 同理）；改编程式 `registry.circuitBreaker(name).executeSupplier()` 免疫。
**数据**（故障注入杀 product 进程）：正常下单 9900 → 12 连发失败 → 熔断 OPEN → **熔断期间下单 90ms 快速失败 + 占位价 100 降级创建**（订单照常、用户无感、不占线程）→ product 恢复 → 半开探活成功 → 金额回 9900、耗时 310ms。**核心交易在下游故障期间不中断**。

### 面试官怎么问、你怎么接

| 追问 | 应答要点 |
|---|---|
| 熔断和降级的关系？ | 熔断是"快失败开关"，降级是"失败后的业务兜底"。本项目熔断触发后走占位价下单 + 对账兜底（工作流1 的补偿机制接住） |
| 为什么编程式不用注解？ | 4 个调用点全在同类 private 方法，注解 AOP 代理拦不到 self-invocation（实测验证失效）；编程式无代理依赖、fallback 即既有 catch，侵入更小 |
| 半开探活怎么设计？ | 打开 10s 后自动转半开，放 3 个探活请求，全成功才关；探活失败自动回 OPEN（实测 OPEN→HALF_OPEN→OPEN 循环） |
| 熔断参数怎么定？ | 滑动窗口 10 次 + 失败率 50%：容忍单次抖动，2 次以上连续失败即熔断；慢调用 2s 捕获下游退化 |

## 五、全链路压测：一个"假错误率"差点骗过我

### 讲什么（60 秒版本）

**背景**：要给系统一个"可解释容量"而不是拍脑袋的 5000 QPS。
**怎么做**：自研 threading 压测器（本机无 k6），黄金路径读 80% + 写 20%，**分层对比法**——同一并发分别打 BFF 入口和直连服务，定位瓶颈在哪一层。
**最大的坑**：第一版数据"BFF 错误率 19.46%"差点得出"BFF 有 19% 故障"的错误结论——**压测器把 HTTP 201 当成了错误**！BFF 写路径返回 201 Created（Nest 默认 POST 状态码），断言只认 200，20% 的写请求全被误判。修正后全档位 **0 错误**。
**真结论**：并发 50→200VU，BFF RPS 不升反降（173→137→114）且 P50 线性恶化（258→694→1624ms = 排队），直连服务层稳定 **375+ RPS、P50 <50ms** → **瓶颈在 BFF 转发层单实例**，服务层（Java+MySQL）容量充足。
**可解释容量**：服务层 >370 RPS（P50<50ms）；BFF 单实例有效容量 ~170 RPS。扩容方向是 BFF 横向多实例 + 连接池调优，不是加 Java 服务。

### 面试官怎么问、你怎么接

| 追问 | 应答要点 |
|---|---|
| 怎么定位瓶颈层？ | 分层对比：同并发下 BFF 入口 vs 直连服务，RPS/RT 差异即转发层开销；再配合并发-吞吐曲线（不升反降 = 排队饱和） |
| 压测器还有什么坑？ | asyncio + 同步 urllib = 假并发（event loop 被阻塞调用拖死，20 分钟只出预热）→ 改 threading 真并发；断言必须覆盖真实成功语义（200/201） |
| 200VU 直连还有 0.41% 错误？ | 单 SKU 高并发下的库存扣减瞬时竞态（乐观锁重试窗口），记录为已知限制——真实压测就该暴露这种边界 |

## 六、告警接入：403 才是第一步

### 讲什么（40 秒版本）

**背景**：熔断/高错误率"发生了才知道"，无主动告警。
**怎么做**：① 修 403——14 个服务 SecurityConfig 放行 `/actuator/prometheus`（安全链只放行 health，最小暴露原则）；② alerts.yml 5 条规则（熔断 OPEN critical/半开抖动/高错误率/高延迟/实例掉线）；③ Alertmanager 分级路由（critical/warning 不同 webhook 通道）+ 熔断状态事件日志埋点。
**验证**：4 核心服务指标端点 200、`resilience4j_circuitbreaker_state` 指标齐全；`promtool check rules` SUCCESS（5 rules）。
**坑**：新 prom/prometheus 镜像 v3 入口不再是 promtool，需 `--entrypoint promtool` 指定版本。

## 七、给面试官的一句话总结（电梯版）

> "智购是一个 16 服务的 AI 原生电商系统。我最想聊的是**怎么用实测数据做工程决策**：交易一致性不是拍脑袋定隔离级别，是故障注入测出来的；熔断不是装个注解，是发现 AOP 对 private 方法失效后改编程式；压测报告里有个 19% 的假错误率，是我自己写压测器时把 HTTP 201 当错误统计出来的——这些坑和数据，比技术名词更能说明我遇到问题时的处理方式：**先复现、再定位、用数据说话**。"

## 附：面试官可能深挖的方向（主动备料）

1. **乐观锁/悲观锁实战**：库存扣减 `UPDATE ... SET stock=stock-#{n} WHERE stock>=#{n}`（原子条件更新）+ 重试；为什么不用先 SELECT。
2. **消息可靠性**：outbox 模式——业务事务里写本地消息表 + MQ 投递 + 定时补偿扫表（RocketMQ）。
3. **状态机**：枚举 transition map + 非法跃迁业务码，为什么不用 Spring StateMachine（简单场景过度设计）。
4. **安全**：JWT 无状态鉴权、日志脱敏 AOP（手机号/身份证掩码）、支付金额服务端计算。
5. **部署**：9 服务 Dockerfile 分层镜像、GitHub Actions 流水线（测试→构建→镜像→部署）、CI 集成测试基建（RocketMQ 服务容器）。
